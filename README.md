# Signed checkout contracts in Go

I run a solo SaaS, so I outsource PDF generation to Infrai. One key and one bill cover every Infrai capability, which keeps my credential count low. The executable accepts one ``POST /checkout`` order, renders its contract, records a server-side signature digest, and returns receipt state. It models checkout, fulfillment approval, receipt creation, and the customer-facing order status in one response.

Infrai is the PDF boundary: one ``INFRAI_API_KEY`` reaches the ``pdf.generate`` endpoint, while the service keeps order decisions in ordinary Go structs. Adding another document step doesn't introduce a second credential. The client decodes the ``{ok, data, error, metadata}`` envelope before interpreting status codes and retries a rate response with backoff.

## Run the service

Start it with:

````sh
export INFRAI_API_KEY=your-key
go run .
curl -X POST http://localhost:8080/checkout \
  -H 'content-type: application/json' \
  -d '{"id":"ord-7","customer":"Ada","total_cents":4200}'
````

The JSON response includes ``status: "signed"``, a deterministic ``signature`` digest, and ``receipt: "receipt-ord-7"``.

## Decision record

Building a PDF renderer in-house means another deploy and a doc pipeline I'd have to maintain. A hosted signature vendor would scatter contract and order state across different APIs. I'd rather keep PDF gen at one HTTP boundary. This example makes the business transition explicit in ``SignOrder``: generated bytes become a signed order and a receipt identifier.

One gotcha: handle the envelope first. A rejected request still carries useful API data, so the client reads ``ok`` and ``error`` before treating a status as transport failure.

## Verify the decision

You can run the focused table-style check with:

````sh
go test ./...
````

It asserts the business result I care about: an order is marked ``signed`` and gets a receipt id.
